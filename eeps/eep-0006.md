# EEP 6 - The standard Edison's code is held to

## Abstract

Edison writes Python and nothing said what standard it was held to. This
document adopts one, whole and at one exact revision: Google's Python Style
Guide, with Google's `pylintrc` as the thing that checks it.

It binds the Python in every repository Edison owns, not only this one. It
records two places where the guide and the linter disagree, and in both the
guide wins.

## Motivation

EEP 1's substitution table reads
`PEP 7 and PEP 8, for code in examples | vacant`, and that was right when it was
written: PEP 7 and PEP 8 govern code inside a proposal, and no EEP contains any.

Then this repository grew a checker. `tools/check-eeps`, `tools/check-python`
and `tests/run-fixtures` are several hundred lines of Python that decide whether
every other document in the series is acceptable, and no document said what made
them acceptable.

That gap was in the law and not in the code. The code already passed `flake8`
and `ruff` at eighty columns before this document existed. But a standard nobody
wrote down is a standard nobody can be held to, and this series has already
watched an unchecked claim rot: the `PEP 12` row in EEP 1 said the template was
vacant for four commits after EEP 3 filled it, because nothing checked the
table.

## Specification

### The pin

Edison follows Google's Python Style Guide as it stands at revision
`3b8822983dc779c498961cc86332a28c07590f64` of `pyguide.md` in
`github.com/google/styleguide`, committed 11-Sep-2026, and Google's `pylintrc`
at that same revision. Later changes to either do not change Edison's standard
until the pin is moved.

### Why this one

EEP 2 ranks what may confirm a thing. The reference publisher, Google, is third.
Established practice in the wider community is fourth. PEP 8 is the practice of
one community, however large. Google publishes a Python style guide, so it
outranks.

This is the same ranking that chose Google's code of conduct over Contributor
Covenant in EEP 5, and Google's sentence case over PEP 1's title case in EEP 3.
The ranking is doing the work, not preference.

The two guides mostly agree. Google's is PEP 8 with departures, and it sets the
same eighty-character line that this series already adopted for Markdown.

### What it binds

The Python in every repository Edison owns.

This is the first EEP that reaches past the series, so the reading has to be
written down rather than assumed. EEP 4 sets the **council's** remit at the EEP
series and says it is "not a charter for the company, for client work, or for
any repository Edison owns". EEP 2 says what every project gets is written once,
for all projects, in this series.

Those agree. The council decides this document; this document binds the
projects. The council does not thereby govern the projects, and EEP 4's remit is
untouched.

Today Edison owns one repository, so the reach is theoretical. It is stated now
because writing it once, for all projects, is what EEP 2 asks and because the
alternative is deciding it again per project.

### The rule of adoption

The guide is read with the substitutions below. Nothing is added and nothing
removed. Where a substitute does not exist the clause is **vacant**: it stays in
the guide, it is skipped, and it is filled as soon as it can be. This is EEP 1's
rule, applied to a third document.

### Substitutions

The guide needs very little. It runs to 3,778 lines and refers to Google's own
tooling four times, three of them inside one illustrative docstring.

| The guide says | Read as |
|---|---|
| `blaze`, `google3`, `//foo/bar:foo_test` in the golden-file example | vacant. The example is teaching a docstring, not a build system |
| "Run `pylint` over your code using this pylintrc" | as it says. `.pylintrc` here is that file at the pin, and `tools/check-python` runs it |
| "Google Python Style" as the name of the thing | Edison's Python style, which is Google's at the pinned revision |

### Where the guide and its linter disagree

Google's `pylintrc` is the tool that checks Google's guide. In two places it
does not match the guide it checks. In both, **the guide is right and the tool
has a defect**, which is the rule EEP 1 already applies to itself against PEP 1.

Both divergences are listed here and in `.pylintrc`'s own header, and
`tools/check-eeps` refuses a `.pylintrc` whose divergences are not these.

**`consider-using-f-string` is disabled.** The guide, section 3.10, permits the
`%` operator and lists it under "Yes":

```python
x = '%s, %s!' % (imperative, expletive)
```

and adds "Use your best judgment to decide between string formatting options".
The check contradicts that. Thirty-eight of the forty-four findings in this
repository's code were this one disagreement.

**`module-rgx` allows a hyphen.** The guide, section 3.16, says "Always use a
`.py` filename extension. Never use dashes". Here the linter is enforcing the
guide correctly, and this repository breaks it: its three entry points are
`tools/check-eeps`, `tools/check-python` and `tests/run-fixtures`.

The owner recorded a departure rather than rename them. They are commands, not
modules: nothing imports them, each carries a shebang, and each is invoked by
the name it has. EEP 2 permits a departure where it is written down and
reasoned, and this is the writing down.

The relaxation is deliberately narrow. Only `module-rgx` changes, so
`invalid-name` still governs every variable, constant, class, argument and
function. This was checked by running the linter against a file with a bad
argument name and watching it fail.

### How it is checked

`tools/check-python` runs `pylint` with `.pylintrc` over the repository's
Python.

`pylint` is not a dependency. When it is absent the tool says so and exits zero,
the way `tools/check-eeps` treats PyYAML: someone without it is not blocked, and
the workflow installs it so the check is never skipped where it decides
anything. A green local run therefore does not prove conformance, and that is
stated rather than hidden.

Two rules in `tools/check-eeps` keep the configuration honest. One refuses a
repository whose `.pylintrc` is missing or has lost the pinned settings. The
other refuses one whose divergences are not the two above, so the file cannot
quietly acquire a third.

### A language that is not Python

Deferred, with a trigger, in EEP 4's style: the first Edison repository written
in another language forces the question. Nothing is invented here for languages
that do not exist.

### What is not covered

Formatting tools and type checking. The guide discusses both and nothing here
needs either yet.

More importantly, most of a style guide is not machine-checkable. The guide
binds; the linter reaches the part of it a linter can reach. Passing
`tools/check-python` is not the same as conforming, and nobody should read it
that way.

## Rationale

The shape is EEP 1's and EEP 5's: a pin, a rule of adoption, a substitution
table, and the decisions adoption forced. A reader who knows how Edison adopts a
process knows how it adopts a standard.

The interesting part is the two divergences, and they came out opposite ways on
purpose. A tool that contradicts its own guide is wrong, and the f-string check
was silenced. A tool that enforces its guide correctly against this repository's
habits is right, and there the owner had to either conform or write a departure.
Treating both as "the linter complained" would have lost the distinction that
matters.

Adopting a standard for code that already passed two other linters may look like
ceremony. It is not. The standard is what makes a future change checkable, and
the first thing this adoption did was find a real violation nobody had noticed.

## Backwards compatibility

The repository's Python changes. Six findings were fixed rather than suppressed,
and five of them are improvements on their own terms: a `yaml.YAMLError` caught
instead of bare `Exception`, an unused parameter removed from
`check_repo_files`, `check=False` made explicit on a `subprocess.run` whose
commands are expected to fail, and an optional import replaced by
`importlib.util.find_spec`, which asks whether PyYAML is installed without
importing it or leaving an unused name behind.

The sixth is a suppression with its reason attached: the optional PyYAML import
inside `parses_as_yaml` cannot be hoisted without making PyYAML a hard
dependency of a checker that has none.

No file was renamed and no command changed its name, which is what the departure
above bought.

## How to teach this

Tell someone: Edison's Python is Google's, pinned. Run `tools/check-python`. If
it disagrees with the guide, the guide wins and the disagreement gets written
down.

## Reference implementation

This repository's `tools/` and `tests/`, which conform. The reference
implementation proper is the first Edison repository that is not this one and is
held to the same standard.

## Rejected ideas

- **PEP 8.** EEP 1 already names it, so the series has heard of it. It ranks
  below the reference publisher under EEP 2, so adopting it would have meant
  departing from Edison's own ranking on the first occasion the ranking was
  consulted about code.
- **Scoping this to one repository as a plain change.** Smaller and it would
  have needed no EEP. It also would have meant deciding the same question again
  for the next repository, which is what EEP 2's "written once, for all
  projects" exists to prevent.
- **Converting thirty-eight sites to f-strings.** Faithful to Google's
  `pylintrc` and unfaithful to Google's guide, and it would have meant
  thirty-eight mechanical edits inside the tool the series depends on.
- **Renaming the entry points to `check_eeps.py` and so on.** Conforms with no
  departure to write. The owner chose the departure; the names are commands and
  renaming them would have changed every reference to preserve a rule written
  for importable modules.
- **Failing when `pylint` is absent.** It would make conformance provable
  locally, at the cost of blocking anyone who has not installed it.
- **Writing a style guide.** The loop EEP 1 exists to end.

## Open issues

- **A green local run does not prove conformance**, because the check skips when
  `pylint` is absent. Only the workflow proves it, and the workflow has never
  run.
- **The departure for entry-point names is against clear text.** The guide says
  "Never use dashes" with no exception for executables. The reasoning is written
  down and the owner made the call, but it is a departure from an explicit rule
  and not from an ambiguity.
- **Nothing checks the guide's unmachineable parts.** Most of it.
- **The reach is theoretical.** This binds every repository Edison owns and
  Edison owns one.
- **How often this pin is reviewed.** EEP 4 answers that for PEP 1's pin, when
  something prompts it. Whether the same applies here is not stated.
