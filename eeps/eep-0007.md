# EEP 7 - What every Edison project gets

## Abstract

EEP 2 says that what every project gets is written once, for all projects, in
this series, that what one project gets is written in that project, and that
anything in neither does not get built. Two documents answer that today. EEP 2
itself binds anyone who builds for Edison, and EEP 6 says what Edison's Python
is held to. Both are about how to decide things. Neither says what a repository
has in it.

This document says that. It is a floor: what every repository Edison owns
already owes before anyone asks what it is for. It settles the questions that
would otherwise be answered again, differently, in each new repository, and it
settles nothing about what any repository does.

Every obligation below is either a rule an accepted EEP states, or a practice
that can be seen working in this repository, and each says which. None of it is
new. What is new is that it is written where EEP 2 says it has to be written
before a second project is allowed to rely on it.

Three of the obligations are ones this repository does not yet fully meet. Those
are marked where they appear rather than dropped or glossed.

## Motivation

The owner asked for the series to be built out far enough that he can start a
project with it. It is not. A builder opening an empty repository today, and
following the rules to the letter, reaches the end of them almost immediately.

EEP 2 tells him the rule: "What every project gets is written once, for all
projects, in this series. What one project gets is written in that project. If
it is in neither, it doesn't get built, and the builder asks."

So he asks. And the answer is that nothing in the series says a repository has a
README, or a license file, or a check, or that generated files are kept apart
from written ones. Those things are true of this repository. None of them is
written as a rule, so under EEP 2 the second repository does not get them, and
whoever builds it fills the gap with whatever he is used to.

That is precisely the failure EEP 2 exists to stop, arriving from the other
direction. EEP 2 guards against an agent inventing what was never decided. The
same sentence, read honestly, also forbids a builder from assuming that what
this repository happens to do was ever decided for anything else.

## Specification

### What this binds

Every repository Edison owns.

This is EEP 6's reading and the reasoning is EEP 6's. The council decides this
document; this document binds the repositories. EEP 4 sets the council's remit
at the series and says it is "not a charter for the company, for client work, or
for any repository Edison owns". That is untouched: nothing here gives the
council authority over what a repository does, only over what every repository
already owes.

### What is settled here and what is settled in the project

Everything below is a floor. What one project gets is written in that project,
as EEP 2 says.

A repository may depart from anything here, and the departure is written down in
that repository with its reason. **Only the council may sign a departure.** EEP
2's departure clause is narrower than it first appears: it covers the owner
departing from a standard in EEP 2's ranking, and says nothing about a
repository departing from an EEP. Left unstated, this section would make its own
floor optional at the discretion of whoever wrote the repository, which is not a
floor. The council decides this document, so the council is who may excuse a
repository from it.

### The entry point

Every repository has a `README.md` in its root. It is the entry point: it says
what the repository is, where its rules are, and where things live.

Any file that tells an agent how to work in the repository points at the entry
point, and names no path inside the repository other than the entry point, so
that files can move without it going stale.

Seen working here: `CLAUDE.md` sends its reader to "the README at the repository
root" and says why it names nothing else. The only paths it gives are the two
Google style guides, which are outside this repository and cannot go stale as it
changes.

### The license

Every repository has a `LICENSE` file in its root stating its terms, and its
README says what those terms cover.

The terms are decided per repository and are not settled here. This repository
is under public domain or CC0-1.0-Universal because EEP 1 settled that for the
series. Nothing in that decision reaches client work, which Edison is in no
position to place in the public domain on a client's behalf.

### Written and generated are kept apart

Anything a tool produces is either not tracked, or tracked together with a check
that refuses it once it no longer matches what produced it. Nothing generated is
edited by hand, and the generated file says so in itself.

Seen working here: `.gitignore` keeps build artefacts out and its comment gives
the rule; rule `R007` in `tools/check-eeps` refuses a tracked artefact, because
ignoring can be overridden with `git add -f` and refusing cannot; `standard/` is
tracked because it is the output this repository exists to publish, and
`tools/build-standard --check` refuses it once it has drifted from the EEPs.

### The checks

Every repository has at least one command that decides whether the repository is
acceptable. It runs locally, and it is wired to run on the host for every push
and every pull request.

Every rule the command enforces names the source it comes from, in a comment
above the rule or in the docstring of the function that holds it. A rule with no
source does not belong in it.

Where a check cannot decide, because something it needs is absent, it says which
and does not claim to have decided.

**This repository does not fully meet the last two.** `tools/check-eeps` opens
by naming the only three sources a rule may come from and stating that a rule
with no source does not belong in the file. Twenty-nine of its thirty-two rules
carry that comment and `R001` carries `PEP 1:793-794` in the docstring of
its function, but `R006` and `R007` give rationale and name no source. Two of
its degradations are silent rather than spoken: without PyYAML it drops rule
`E003` and still prints "no findings", and `check_no_artifacts` returns nothing
when `git ls-files` fails. `tools/check-python` and `tools/check-adoption` both
print their reason and exit zero, which is the behaviour this section asks for.

The host half has never happened here. The workflow is wired and triggers on
every push and pull request; no job has ever started, because GitHub refuses
them over the account's billing. So that clause rests on PEP 1's editor step as
EEP 1 substitutes it, and not on anything seen working.

### A rule is seen failing before it is trusted

A rule that has never been seen failing has never been tested. Every rule has
something that provokes it, and the provocation is kept: a fixture where one
file can provoke it, and otherwise a record, in the change that introduced or
repaired the rule, of how it was provoked by hand.

Seen working here: `tests/fixtures/` holds one directory per file-level rule,
twenty-five of them, each the known-good file with exactly one thing wrong.
`tests/run-fixtures` reads the rule identifiers out of the checker itself, so a
file-level rule with no fixture is a failure in its own right. The seven
repository-level rules cannot be provoked by one file and the runner exempts
them; each has instead been provoked by hand, and the change that did so says
how.

### What is taken from outside is pinned, not copied

Where a repository takes a standard, a configuration or a text from outside, it
adopts it at one exact revision. It does not restate it in its own words. A
restatement drifts from its original in silence; a pin shows drift plainly, as a
newer revision existing.

Where a working copy is unavoidable, because a tool has to read the file
locally, the copy names the revision it was taken from and every divergence from
it, and something refuses a divergence that is not recorded.

Seen working here three times as a pin with no copy: EEP 1 pins PEP 1, EEP 3
pins Jekyll's front-matter format, and EEP 6 pins Google's Python style guide.
Twice as a working copy: `tools/pylintrc`, which is Google's file at the pin
with its two divergences recorded in its own header, and `LICENSE`, which is the
CC0 text itself because a license has to be carried to be granted. A fourth pin,
EEP 5's of Google's code of conduct, is written but not accepted and so binds
nothing yet.

The refusal on the working copy is weaker than this section asks. `R004` reads
only divergences that declare themselves with an inline marker, so it cannot see
one that declares nothing.

### How a change reaches the main branch

On a branch, by pull request. Nothing is pushed to the main branch directly.

Seen working here: this repository's `CLAUDE.md` requires it, and `git log main
--first-parent --no-merges` returns exactly one commit, the initial import.

### What is not settled here

The language a repository is written in, and the standard that language is held
to. EEP 6 answers that for Python and defers every other language to the first
repository that needs one.

Anything about what a repository is for, what it contains, or how it is built.
This document says a repository has checks; it does not say what they check.

## Rationale

The type is `Process`. The pinned PEP 1 decides it. A Standards Track PEP
"describes a new feature or implementation for Python"; a Process PEP "describes
a process surrounding Python", covers "procedures, guidelines, changes to the
decision-making process, and changes to the tools or environment used in Python
development", and unlike an Informational PEP is "more than recommendations", so
that "users are typically not free to ignore them". A floor for repositories is
a guideline about the environment work is done in, and it must not be ignorable.
EEP 6, the only other EEP that binds repositories rather than proposals, is
`Process` for the same reason.

Each obligation is written as a rule with its evidence attached, rather than as
advice. EEP 2 makes a thing confirmable in one of two ways: "a source anyone can
open says so", or "it can be seen working in a real project". This document
leans mostly on the second, because the first is thin here: the EEPs it cites
are in a private repository that nobody outside can open, so today only the
outside sources the series pins satisfy EEP 2's first route in full. The real
project is this one, and one instance is a weak base for a generalisation. That
is stated in the reference implementation and in the open issues rather than
hidden.

Three obligations are ones this repository does not yet meet, and they are
marked in place. The alternative was to weaken each rule until this repository
passed it, which would have written the floor down at the level of whatever
happened to be true on the day, or to state them cleanly and let the reader
discover the gap. Naming the gap keeps the rule honest and keeps the repository
honest, which is the arrangement EEP 6 already uses when it records that a green
local run proves nothing without `pylint`.

The document is short on purpose. EEP 2's second protected thing is simplicity,
"Nothing gets added that is of no use to this project", and the failure EEP 1's
motivation names is a process that "grew elaborate before it was used".
Everything here is something a repository cannot be worked in without. Several
practices this repository follows are deliberately left out for that reason, and
named below.

## How to teach this

Tell a builder: before you decide anything about a new Edison repository, this
document says what it already owes. It is a floor, it is short, read it once.
Everything else about that project is written in that project, and if it is in
neither, ask.

## Reference implementation

The first Edison repository that is not this one, built to this document and
shipped.

Until then this document generalises one repository's practice. EEP 3 states the
bar: a reference implementation is "a real project that used the proposal", and
an EEP may not become `Final` until that project has shipped. It may be accepted
before then. As a Process EEP it is more likely to settle at `Active`, as EEP 1,
2, 3, 4 and 6 did, since a floor is never meant to be completed.

## Rejected ideas

- **A template repository to copy from.** The obvious alternative and the one
  this document exists instead of. A copy drifts from its original in silence,
  which is the reason EEP 1 pinned PEP 1 rather than copying it. The same
  objection applies to a repository copied at the start of a project and never
  compared to its source again.
- **Extending this repository's license to every repository.** EEP 1 settled
  public domain or CC0-1.0-Universal for the series. Applying that to client
  work would dedicate somebody else's property to the public domain, which is
  not Edison's to do.
- **Naming a language, a framework or a directory layout.** EEP 2 says Edison is
  "Not loyal to any one framework". A floor that names one is not a floor.
- **Writing this in `CLAUDE.md` instead.** It would be read, and it would bind
  nothing: EEP 2 says what every project gets is written in this series, and a
  file in one repository is not that.
- **Waiting for the second repository.** Defensible, and the argument for it is
  that a generalisation drawn from one instance is a guess. The argument against
  it is EEP 5's, on deferring the code of conduct until the repository had a
  host: it leaves the writing to the week it is first needed, which is the worst
  time. It is also circular here, because under EEP 2 the second repository
  cannot rely on any of this until it is written.
- **Weakening the three rules this repository does not meet.** It would let the
  document claim a clean evidence base. It would also write the floor down at
  whatever height this repository happened to be standing on the day, which is
  the opposite of what a floor is for.
- **Requiring a change history in every repository.** Required of every EEP by
  EEP 3, and one of this repository's strongest habits. Left out because a
  repository's history is already in its version control, and the series needs
  the section only because an EEP is read as a document rather than as a diff.

## Open issues

- **Which of this repository's practices generalise is the drafting agent's
  reading.** The inventory was taken by reading this repository, and each item
  above names what was read. Which of them belong to a series of proposals and
  which to any repository is a judgement, and it is the agent's. The owner has
  not been asked item by item.
- **Nothing here has been applied to a second repository.** Every obligation is
  confirmed as this repository's practice and none is confirmed as workable
  anywhere else.
- **Three obligations outrun their evidence**, and are marked where they appear:
  a check that is silent when it cannot decide, a check that runs on the host,
  and a refusal that catches an undeclared divergence in a working copy.
  Whether to fix the repository, weaken the rule, or leave the gap recorded is
  the council's.
- **The commit message form is unwritten.** On branches, this repository's
  commit subjects carry a type and an optional scope without exception. On the
  main branch they do not: ten of the eleven first-parent subjects are merge
  subjects with no type. No document requires either. It is left out above
  because writing down a habit nobody has decided is the gap-filling EEP 2
  forbids, and it is raised here because the habit is real and the silence is
  odd.
- **The standard is in a private repository.** A repository built to this
  document is told to follow `standard/STANDARD.md`, which today nobody outside
  can open. Whether a client repository names the standard, carries the part of
  it that applies, or does something else is undecided. The same fact weakens
  EEP 2's first route to confirmation for everything in this series.
- **Whether the checks obligation is proportionate.** A command that decides
  whether the repository is acceptable is cheap for a series of text files and
  may not be for a small site. Nothing here scales it to the size of the work.
- **Whether a repository must say which EEPs bind it.** This document says a
  repository is bound; it does not require the repository to record that it is.
