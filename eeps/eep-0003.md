# EEP 3 - EEP Template and Format

## Abstract

EEP 1 adopts PEP 1 whole and marks PEP 12, the template, vacant. This
document fills that vacancy. It gives an author a skeleton to copy and an
editor the form to check against, and it settles the questions that
arise when PEP 1's rules, written for reStructuredText, are applied to
Markdown.

It adds no step to the process and removes none. Everything here is
either PEP 1 at the pinned revision, a rule of the reference publisher
EEP 2 names, or a decision of the owner's recorded as such.

## Motivation

The vacancy is not cosmetic. PEP 1 tells an editor what to do with a
proposal that arrives in the wrong shape: "If the PEP isn't ready, an
editor will send it back to the author for revision, with specific
instructions. If reST formatting is a problem, ask the author(s) to use
PEP 12 as a template and resubmit."

Under EEP 1 that instruction points at nothing. An editor who follows the
adopted process to the letter reaches a step that cannot be performed.
EEP 1 already lists a template EEP among its vacant steps; this document
removes it from the list.

There is a second reason. PEP 1 requires a header preamble in RFC 2822
style and says nothing about how a Markdown file carries one. EEP 1 and
EEP 2 answered that question in practice, by fencing their headers in
`---`, but nothing wrote the answer down. Under EEP 2 an unwritten answer
is exactly the kind of gap that gets filled by whoever is next in the
room.

## Specification

### What this document is

Two things, as PEP 12 is two things: instructions for writing an EEP, and
a skeleton to copy. It is also the third thing PEP 1 makes it, the
document an editor hands back to an author whose file is in the wrong
shape.

It is not a Markdown tutorial. PEP 12 teaches reStructuredText because
reStructuredText is unfamiliar and fails silently. Markdown's rules are
published by Google, whom EEP 2 names as the reference publisher, and
this document points at them rather than restating them. A restatement
drifts from its original in silence, which is the reason EEP 1 pinned
PEP 1 instead of copying it.

### File name and number

An EEP is one file, `eeps/eep-NNNN.md`, where `NNNN` is the number padded
to four digits. PEP 1: the number is "the next available PEP number not
used by a published or in-PR PEP", and "numbers below 100 are
meta-PEPs". A process EEP about the series itself is a meta-EEP and takes
a number below 100.

The number in the `EEP:` header and the number in the filename must
agree.

### The header preamble

PEP 1 is exact about this: "Each PEP must begin with an RFC 2822 style
header preamble. The headers must appear in the following order."

The order below is PEP 1's, with EEP 1's substitutions applied. A header
marked optional may be left out entirely. Every other header must be
present, though its value may be empty when there is nothing to put
there yet.

| Header | Required | What it holds |
|---|---|---|
| `EEP` | yes | the number, matching the filename |
| `Title` | yes | at most 44 characters |
| `Author` | yes | `Name` or `Name <address>`, one per line |
| `Sponsor` | no | omit it when an author already has write access |
| `EEP-Delegate` | no | appointed by the council. Never an agent |
| `Discussions-To` | yes | the pull request thread. Empty until one exists |
| `Status` | yes | one of the nine below |
| `Type` | yes | `Standards Track`, `Informational` or `Process` |
| `Requires` | no | the EEPs this one depends on |
| `Created` | yes | `DD-MMM-YYYY`, the date the number was assigned |
| `Post-History` | yes | `DD-MMM-YYYY` dates, linked to their threads |
| `Replaces` | no | the EEP this one renders obsolete |
| `Superseded-By` | no | the EEP that rendered this one obsolete |
| `Resolution` | no | required for Standards Track only. Only the owner fills it |

`Status` is one of `Draft`, `Active`, `Accepted`, `Provisional`,
`Deferred`, `Rejected`, `Withdrawn`, `Final` or `Superseded`. A new EEP
is always `Draft`. Only the council changes it.

Two of PEP 1's headers are vacant here and so are absent from the table.
`Topic` is vacant because EEP 1 marks the categories vacant and no EEP
yet needs categorising. `Python-Version` is vacant under EEP 1's
substitution table. Per EEP 1 a vacant step "stays in the process, it is
skipped for now, and it is filled as soon as it can be", so both keep
their places in the order above and neither is written in a file.

### Writing the preamble in Markdown

PEP 1 needs no delimiter because a `.rst` PEP's headers are parsed by a
build system that expects them. A Markdown file has no such convention:
a bare `Title: x` at the top of a `.md` file is an ordinary paragraph.

Edison therefore adopts YAML front matter, as Jekyll defines it, at
revision `8c3934fd0271dc709b3d3b91f8b78e12274eeae6` of
`docs/_docs/front-matter.md` in `github.com/jekyll/jekyll`. Jekyll's
definition: the block must be the first thing in the file and must take
the form of valid YAML set between triple-dashed lines. Jekyll is also
what GitHub Pages runs, so the same pin serves the series when it is
published.

Adopting the format is not a commitment to build a site. If the series is
ever rendered, this is the pin that says how.

One consequence has to be stated. PEP 1 wraps its longer `Status`,
`Author` and `Post-History` values across lines by RFC 2822 continuation.
YAML folds a continuation line only when it is indented further than its
key, so a wrapped value must be indented. `tools/check-eeps` parses the
block and will say so when it is not.

An unfilled required header is left with an empty value. It is not
written `vacant`: EEP 1 gives that word a specific meaning, a step whose
substitute does not exist, and an unopened discussion thread is not that.

### The title

At most 44 characters, and, in PEP 1's words to an editor, it "should
accurately describe the content".

The `Title:` header and the level one heading say the same thing. The
heading is written `# EEP <N> - <Title>`, so that the two cannot drift
apart.

### The sections

PEP 1 lists the sections and their order. Note its wording: "Each PEP
should have the following parts/sections". Three of them carry their own
condition, and an EEP that does not meet the condition leaves the section
out rather than filling it with "none".

| Section | When |
|---|---|
| Abstract | always. About 200 words |
| Motivation | always. PEP 1 rejects proposals whose motivation is thin |
| Specification | always |
| Rationale | always. Why this design, and what else was considered |
| Backwards compatibility | only if the EEP breaks something that exists |
| Security implications | only if there are security concerns |
| How to teach this | always here. PEP 1 calls it helpful; EEP 2 turns it into the way an agent is told what to do |
| Reference implementation | always. See below |
| Rejected ideas | always. What was proposed and not taken, and why |
| Open issues | always. Empty it before asking for a decision |
| Acknowledgements | always |
| Footnotes | only if there is anything to collect |
| Change history | always |
| Copyright | always |

Under EEP 1, a reference implementation is "a real project that used the
proposal", and an EEP may not become `Final` until that project has
shipped. An EEP may be accepted before then.

PEP 1's own list numbers Footnotes 13 and Copyright 15, and leaves Change
History unnumbered between them. The gap is a slip in the pinned text.
The section's position, between Footnotes and Copyright, is what the list
shows and is what this document follows.

### Where Google governs and where PEP 1 governs

PEP 1 is the process. It decides what an EEP contains, in what order, and
what happens to it. Nothing below changes that.

Prose style is a different question, and EEP 2 answers it with a ranking.
The reference publisher, Google, ranks third; established practice in the
wider community ranks fourth. PEP 1's own habits of prose are the
practice of one community. So where the two differ on style, Google
governs.

Two differences are known, and both are settled here:

- **Headings.** PEP 1 names its sections in title case. Google requires
  sentence case for headings. Sentence case wins, which is why this
  document's sections read "How to teach this" and not "How to Teach
  This". Document titles are names and keep the capitals their author
  gave them.
- **The en dash.** Google's developer style guide says of the en dash:
  "Don't use. Instead, use a hyphen or the word to." PEP 1 says nothing
  about the character, so there is nothing to weigh against it.

Dates are not a style question. `DD-MMM-YYYY` is a structured field of
the adopted process and PEP 1 governs it. Note that PEP 1's own change
history is dated `2026-02-02`, which breaks the rule PEP 1 states a few
hundred lines earlier. The rule binds; the example does not.

For everything else, open Google's Markdown style guide and the Google
developer documentation style guide. Do not work from a summary of them,
including this one.

### Change history

PEP 1: "whenever you update the `Post-History` header for major changes,
add a new bullet item in newest-first (i.e. reverse chronological) order,
using the same `DD-MMM-YYYY` format, with sub-bullets summarizing the
changes."

PEP 1 leaves the section to the author's discretion. Edison does not: a
change without an entry is not finished.

### Copyright

PEP 1: "Each new PEP must be placed under a dual license of public domain
and CC0-1.0-Universal". Edison follows it. Every EEP ends with PEP 1's
own notice, reproduced in the skeleton below and in no other wording.

### Auxiliary files

PEP 1 names them `pep-XXXX-Y.ext`, a serial number starting at 1, or
places them in a subdirectory `pep-XXXX` where "there are no constraints
on the names used in files". Substituted: `eep-NNNN-Y.ext`, or a
directory `eeps/eep-NNNN/`.

An image carries its alternative text, which in Markdown is written
`![alt text](path)`.

### CODEOWNERS

PEP 1 has an author "update `.github/CODEOWNERS` such that any
co-author(s) or sponsors with write access to the PEP repository are
listed for your new file", and has an editor check it before merging.

The repository has no host yet, so nobody has write access to it and the
entries are placeholders. `tools/check-eeps` checks that every EEP has a
line, which is the part of the step that can be performed today. This is
recorded in EEP 1's vacant steps.

### What an editor checks

PEP 1 gives the list, and is clear about its limit: "PEP editors don't
pass judgment on PEPs. They merely do the administrative and editorial
part." An editor may be an agent. Deciding is the council's, and the
council is not an agent.

Under EEP 1's substitutions the checks are:

1. The EEP has an author with write access, a sponsor, or a sponsor the
   council approved for it.
2. It is sound and complete. The ideas make sense, whether or not they
   look likely to be accepted.
3. The title describes the content.
4. The file is `eeps/eep-NNNN.md`.
5. Everyone listed as author or sponsor who has write access is in
   `.github/CODEOWNERS`.
6. The language has no obvious defects.
7. Any project described as supporting the EEP has said so itself. PEP 1
   asks for this "to avoid a PEP accidentally portraying a project as
   supporting a PEP when in fact the support is based on conjecture",
   which is EEP 2's root rule arriving by another road.
8. The number is the next available one, and below 100 for a meta-EEP.
9. The type is one of the three and the status is `Draft`.
10. `tools/check-eeps` passes.

### The skeleton

Copy the block below into `eeps/eep-NNNN.md` and replace what is in angle
brackets. Delete the optional headers you do not use, and the conditional
sections that do not apply.

```markdown
---
EEP: <the next available number>
Title: <at most 44 characters>
Author: <name, or name and address>
Sponsor: <omit unless the author lacks write access>
EEP-Delegate: <omit unless the council has appointed one>
Discussions-To: <the pull request thread, or empty>
Status: Draft
Type: <Standards Track | Informational | Process>
Requires: <EEP numbers, or omit>
Created: <DD-MMM-YYYY>
Post-History:
---

# EEP <N> - <Title>

## Abstract

<About 200 words on the issue being addressed.>

## Motivation

<Why what exists today does not answer the problem. A thin motivation is
grounds for rejection.>

## Specification

<The technical specification, detailed enough that the repositories this
EEP changes could be built or changed from it alone.>

## Rationale

<Why these decisions and not others. What else was considered, and the
objections raised.>

## Backwards compatibility

<Only if this EEP breaks something that exists: what breaks, how badly,
and what you propose to do about it. Delete this heading otherwise.>

## Security implications

<Only if there are security concerns. Delete this heading otherwise.>

## How to teach this

<What to tell someone, person or agent, so they can apply this EEP.>

## Reference implementation

<The real project that used this proposal. The status may not become
Final until that project has shipped.>

## Rejected ideas

<What was proposed and not taken, and why, so it is not proposed again.>

## Open issues

<What is still undecided. Empty this section before asking the council to
decide.>

## Acknowledgements

<Who helped, including people who are not co-authors.>

## Footnotes

<Footnotes cited above, and link targets kept out of the prose. Delete
this heading if there are none.>

## Change history

- <DD-MMM-YYYY>
    * <What changed. Newest entry first.>

## Copyright

This document is placed in the public domain or under the
CC0-1.0-Universal license, whichever is more permissive.
```

## Rationale

The template is a skeleton and a set of rulings, not a tutorial, because
the two jobs PEP 12 does are not equally needed here. Its markup tutorial
exists because reStructuredText is unfamiliar and its errors are quiet.
Markdown has a published reference, and EEP 2 already says which one
Edison follows.

What is left is the part PEP 12 does that nothing else can: deciding the
questions PEP 1 leaves to the format. How a Markdown file carries an RFC
2822 preamble. How a vacant header is written. Which authority wins when
PEP 1's prose habits and Google's rules disagree. Those are answered once
here rather than re-derived by every author.

Every ruling above is derived rather than invented, and says from what.
Where a ruling is the owner's own call, it says that too. The alternative
was a document that reads well and settles nothing, which is the failure
EEP 1's own motivation describes.

## Backwards compatibility

This EEP changes documents that were already written.

Sentence-case headings and the ban on the en dash apply to EEP 1 and
EEP 2, which used title case and U+2013. Both were changed in the same
pull request as this document, so that no EEP in the series fails the
rules the series states. The changes are to headings and one character in
each title; no wording moved.

The `---` front matter both files already used is unchanged. This
document gives it a source; it does not give it a different shape.

## How to teach this

Tell an author: copy the skeleton at the end of EEP 3, fill it in, and
run `tools/check-eeps`. Tell an editor: EEP 3 lists what you check, and
judging is not on the list.

## Reference implementation

This document is written to its own skeleton, which is the first test it
has to pass. The reference implementation proper is the first EEP another
author writes from the skeleton without an editor having to correct its
form.

## Rejected ideas

- **Copying PEP 12's text.** PEP 12 is public domain, so it was allowed.
  A copy drifts from its original silently, which is the reason EEP 1
  pinned PEP 1 rather than copying it. The same reasoning applies here.
- **Restating Google's Markdown rules in this document.** It would make
  the document self-contained and wrong within a year. EEP 2 ranks the
  reference publisher; a pointer stays correct.
- **Inventing a status or a section PEP 1 does not have.** EEP 1's rule
  of adoption is that no step is added and none removed. A template is
  not the place to breach it.
- **Leaving the front-matter fence undocumented.** It was already in use
  in both EEPs and sourced by nothing. Leaving it that way is what EEP 2
  exists to prevent.
- **Recasing the `Title` header along with the headings.** Google asks
  for sentence case in titles too, but a document's title is its name,
  and renaming EEP 1 and EEP 2 is a larger change than a format ruling
  should make on its own. Raised as an open issue instead.

## Open issues

- **Whether document titles should be sentence case too.** Google's rule
  covers titles as well as headings. This document exempts them on the
  grounds that a title is a name. That is a reading, not a ruling, and
  the owner has not been asked.
- **Whether adopting Jekyll's front-matter format implies adopting
  Jekyll.** This document says it does not. If the series is ever
  published, that decision should be revisited deliberately rather than
  inherited from here.
- **`[TOC]`.** Google's Markdown style guide asks for a table of contents
  directive after a document's introduction. `[TOC]` is a Gitiles feature
  that GitHub does not render, and PEP 1 puts the Abstract first, leaving
  no introduction to place it after. Nothing is done about it.
- **Auxiliary files have never been used.** The naming rule above is
  substituted from PEP 1 and has not been tested by anything real.
