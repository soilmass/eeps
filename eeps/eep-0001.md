# EEP 1 - EEP Purpose and Guidelines

## Abstract

EEP stands for Edison Enhancement Proposal. An EEP is how anything that binds
more than one Edison project, or changes how Edison works, gets proposed,
decided and recorded.

Edison does not define its own process. It adopts Python's PEP 1, "PEP Purpose
and Guidelines", whole and at one exact revision. This document holds the pin,
the substitutions needed to read PEP 1 as Edison's, and the few decisions
adoption required. Where this document and the pinned PEP 1 seem to differ on
process, PEP 1 is right and this document has a defect.

## Motivation

Every process Edison's owner wrote for himself grew elaborate before it was used
and was then rebuilt from the start. Adopting a process that already exists,
that has been in use since 2000, and that agents are likely to know already ends
that loop. The last point can be tested by asking any agent to describe PEP 1.
The work that remains is substitution, not design.

## Specification

### The pin

Edison follows PEP 1 as it stands at revision
`74fc18d540c2ea9d2a6f1ba852d0a56e10e1057d` of `peps/pep-0001.rst` in
`github.com/python/peps`, committed 07-Aug-2026. Later changes to PEP 1 do not
change Edison's process until the pin is moved.

### The rule of adoption

PEP 1 is read with the substitutions below. No step is added and none is
removed. A step whose substitute does not exist yet is **vacant**: it stays in
the process, it is skipped for now, and it is filled as soon as it can be.

### Changing this process

A change to this document, including moving the pin, is proposed as a Process
EEP or as an update to this one, and the council decides it.

### What stays out of the series

PEP 1 says most enhancements and fixes do not need a proposal and go to the
issue tracker. The same holds here. A decision inside a single client's project
stays in that project's own repository and never enters the series.

### Who may do what

Anyone may read and anyone may propose, including the public once the repository
is public. Only the council, or a delegate the council appoints, decides. An
agent may be an author, an editor or a sponsor, and is never a delegate and
never the council.

## Rationale

PEP 1 was chosen on two tests, in this order: agents already know it, and it can
be followed to the letter. It also fits on its own terms. It began with one
person holding final say and later moved to an elected council without changing
its shape, which is the path Edison expects to take. It already has the three
types Edison needs. It already separates editors, who check form and never
judge, from the council, which judges. It already requires that a Standards
Track proposal be proven by an implementation before it is Final.

PEP 1 does not invite outsiders to use it. It says other parts of the Python
community may use the process to coordinate design across multiple projects.
Edison is not part of that community. It borrows the process, which PEP 1's
public domain dedication permits.

## How to teach this

Tell an agent: "This repository follows PEP 1 as adopted by EEP 1. Read EEP 1's
substitution table, then apply PEP 1." The agent needs nothing else to begin.

## Rejected ideas

- **A procedure composed from several sources.** One was drafted, drawing on
  AIP-1, PEP 1, the W3C change classes, MADR and ISO's systematic review. It was
  one more invented process, which is the loop this document exists to end.
- **Forking Google's AIP system.** The best fit for a body of standing guidance,
  and built to be forked, but the least known to agents of the three finalists.
- **Rust's RFC process.** Well known, and it has the one thing PEP 1 lacks, a
  mandatory final comment period. It has no types, and the waiting period was
  judged to matter less than types and familiarity.
- **Copying PEP 1's text.** PEP 1 is public domain, so this was allowed. A copy
  drifts from its original silently. A pin shows drift plainly, as "a newer
  revision exists".
- **Naming the series after a single project.** The process covers every
  repository Edison owns, so it carries Edison's name.

## Open issues

- **The vacant steps**: a public discussion venue. The repository is private, so
  "publicly available" is still vacant as this document's substitution table
  says. The template EEP, the governance EEP, the code of conduct and the
  repository's checks are no longer vacant, and topics are now deferred with a
  trigger in EEP 4 rather than vacant.
- **No workflow run has succeeded.** The repository is private, so GitHub
  Actions draws on the account's allowance, and the account's Actions billing
  has not been settled. The checks run locally and pass. They will run on the
  host once the billing is settled or the repository is made public.
- **`Discussions-To` is empty in every EEP.** The repository now has pull
  request threads, which is what EEP 1 substitutes the discussion thread for,
  but no EEP has been given its own thread yet.
