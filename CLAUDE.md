# CLAUDE.md

This file tells you how to work in this repository and how to grow it. It names
no file except the entry point, because the files will change and this file
should not have to.

## Find the rules

1. Read the README at the repository root. It is the entry point and says where
   the rules live.
2. Read every document it names as rules, in full, before you do anything else.
   They outrank this file. Where this file seems to differ from them, they are
   right.
3. If there is no entry point, or it names no rules, stop and ask the owner for
   them. Do not write the rules yourself.
4. The rules adopt an outside process at a pinned revision. When you need to
   know what that process says, open the pinned link and read it. Your memory of
   it is not a source.

## Before you add or change anything

Work through these in order. Stop at the first one that fails.

1. **Is it written?** What you are about to do is in the owner's request, in the
   rules, or in the pinned process. If it is in none of them, do not do it. Ask.
2. **Does it need a proposal?** The adopted process says most changes do not. It
   needs one only if it binds more than one project or changes how the owner
   works. Otherwise it is a plain change.
3. **Can every claim be confirmed?** Each statement of fact you write names a
   source anyone can open, with the place in it, or something that can be seen
   working. Open the source before you cite it. Another agent agreeing confirms
   nothing.
4. **Is it of use now?** If nothing current calls for it, leave it out.

## How this repository grows

When the owner gives you a task, do that task. When he tells you to build the
repository out, or gives no task, do this:

1. **Survey.** List what the rules say should exist and does not: steps marked
   vacant, open issues, missing parts of the required format, links that do not
   open.
2. **Choose one.** Take the item that something real is waiting on. If nothing
   is waiting on any of them, say so, show the list, and ask the owner to
   choose.
3. **Propose it.** Work on a branch. If check 2 says it needs a proposal, write
   it as a draft by the adopted workflow. If not, make the plain change. Open a
   pull request that states the need, the sources you opened, and your
   unconfirmed ideas.
4. **Stop.** Do not start another item while one is waiting for the owner's
   decision.

## Your ideas

You will have ideas that come from neither the owner nor a source. Do not build
on them. End every reply and every pull request with a list headed "Mine,
unconfirmed" that names each one, and wait for a yes or a no.

## What you may and may not do

- You may author a proposal, check a proposal's form as an editor, and sponsor
  one.
- You never decide. Do not set a status other than draft, and do not record a
  resolution. Only the owner does.
- Changes reach the main branch by pull request. Do not push to it.

## Standards

The rules rank the standards that can confirm something. Follow that ranking.
For Markdown and prose the reference publisher's guides are:

- Google's Markdown style guide, `docguide/style.md` in
  `github.com/google/styleguide`.
- The Google developer documentation style guide, `developers.google.com/style`.

Open them; do not recite them. Where one of them disagrees with the format the
adopted process requires, stop and ask. The owner either follows the guide or
writes down a departure.

## This file

This file changes the way everything else does: by pull request, decided by the
owner. Keep it under 200 lines, which is the target Claude Code's documentation
gives. Keep it free of paths: if a file needs naming, name it in the entry
point.

## Before you say you are done

- What you wrote meets every format requirement of the adopted process, checked
  against the pinned text and not from memory.
- Its change history has an entry for what you changed.
- Every link you added opens, and says what you claimed it says.
- Your reply ends with "Mine, unconfirmed", even if the list is empty.
